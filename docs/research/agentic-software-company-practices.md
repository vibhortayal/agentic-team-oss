# Checks, not personas, make agent code shippable

> Written in November 2026 as an evidence review of an earlier draft of this repo. Codes C1 to C6 refer to design questions that draft had open (acceptance, spec size, round limit, test locking, who merges, team shape); all are now settled in [principles.md](../../principles.md) and the playbooks.

Organisations that get production-quality software out of coding agents rely on a small set of mechanical controls, and they rarely add more agent personalities. They keep **one agent writing code at a time**. They give every change an **independent checker that starts with a fresh context**. They accept work only through **automated checks the building agent cannot edit**: tests, linters, structural architecture tests and security scanners. And they keep **a human deciding what merges**, widening agent autonomy only gradually. This repo's design already gets the hardest parts right. Its maker-checker review matrix, read-only tests (C4), "Verifier PASS plus green CI" acceptance (C1), three-round stop rule (C3) and owner-merges-by-default (C5) all match the best evidence available as of November 2026. Its weak points are a different kind of risk. The evidence shows agent "slop" mostly arrives as **slow growth in complexity, duplication and convention drift that passing tests never reveal**, and the design currently lets exactly those findings through as non-blocking "notes". It also has nothing yet on architecture enforcement, dependency checks beyond the foundation draft, UI/UX quality, or measuring code health over time. On the open question C6, the measured evidence favours **one builder per ticket plus an independent Verifier** over the full Architect/Implementer/Verifier trio for routine work. The Architect should be kept only as the coordinator of multi-unit builds from a full spec. Most of the supporting evidence is vendor guidance or observational data rather than controlled trials, so the recommendations below are well-grounded judgements, not proven results.

**How to read the evidence labels.** Each key claim carries a grade and a date. **[M]** means a measured result (a study, benchmark or telemetry with numbers). **[P]** means a practitioner or vendor recommendation, including official product documentation. **[U]** means unverified: seen only in a secondary source, or not opened by the researchers. Vendor-run benchmarks are flagged as such, because the vendor usually wins its own test. All sources were checked on 10 November 2026 unless marked otherwise.

## Leading teams keep one writer and put many independent eyes on it

The single most consistent finding across Anthropic, OpenAI, Google and Cognition is that **parallel agents help with reading, research and review, but code writing should stay with one agent per piece of work**. Anthropic's multi-agent research system beat a single agent by **90.2%** on breadth-first research, but used about **15 times** the tokens of a chat. Token spend alone explained 80% of performance differences on its browsing benchmark, and Anthropic says plainly that "most coding tasks involve fewer truly parallelizable tasks than research" [M, Jun 2025] ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). OpenAI's agent guide says to "maximize a single agent's capabilities first" and to split only when instructions become a tangle of conditions or tools overlap [P, c. Apr 2025] ([OpenAI](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)). Cognition, the company behind the Devin coding agent, argued in 2025 that parallel writers make conflicting hidden decisions. By April 2026 it had settled on a middle position: **writes stay single-threaded**, and other agents contribute by searching, reviewing and advising. Reviewer agents that see only the diff, with a clean context, find more subtle issues [P, Apr 2026] ([Cognition](https://cognition.com/blog/multi-agents-working)). Claude Code's own documentation says experimental "agent teams" use "significantly more tokens". It also says that for sequential tasks or same-file edits, "a single session or subagents are more effective" [P, current] ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)).

The measured evidence on **job-title persona teams** is unflattering. A UC Berkeley study (MAST, NeurIPS 2025) annotated 1,642 runs of seven multi-agent frameworks and found **failure rates of 41% to 86.7%**. The two classic "software company" simulations, ChatDev and MetaGPT, failed 66.7% and 60.0% of programming tasks. Failures clustered in system design (44.2%, including agents disobeying their role), communication between agents (32.3%) and verification (23.5%). Adding a verification step lifted success by 15.6 points, while rewriting role descriptions added only 9.4. The authors conclude that reliability needs "structural redesign, not just prompts" [M, Mar–Oct 2025] ([arXiv 2503.13657](https://arxiv.org/pdf/2503.13657)). A Peking University benchmark built 50 real Python projects from requirement documents [M, Nov 2025] ([arXiv 2511.04064](https://arxiv.org/html/2511.04064v1)):

| Team shape | Requirements implemented |
|---|---|
| Single agent | 45.7% |
| **Developer + Tester** | **49.5%** |
| Designer + Developer + Tester | **27.7%** |

The Designer hurt results because the developer followed the Designer's blueprint over the actual requirements. The lesson is that splits defined by **independent verification** (a tester, a reviewer, a critic) or by **context isolation** (a read-only explorer) help. Splits defined by job titles add handoffs where errors spread.

Memory practice has converged on **files in the repository, not long chat sessions**. Anthropic's guide to long-running coding agents uses a progress file, a JSON feature list, descriptive git commits and a start-up script, so each fresh session re-orients from the repository. It warns that summarising a long conversation "isn't sufficient" to brief the next agent. It also states "It is unacceptable to remove or edit tests" [P, Nov 2025, updated Oct 2026] ([Anthropic](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Google's Elephant-Goldfish Model, published 22 October 2026, splits roles by how long their memory lasts. One long-lived "Elephant" holds the design and writes no code. Fresh "Goldfish" sessions critique the design document without sharing the designer's assumptions [P, Oct 2026] ([Google](https://opensource.googleblog.com/2026/10/introducing-elephant-goldfish-model-plugin.html)). Google reports "thousands of Googlers" use it, but **publishes no measured results**. GitHub frames multi-agent failure as a distributed-systems problem and calls typed, structured handoffs "table stakes" [P, Feb 2026] ([GitHub](https://github.blog/ai-and-ml/generative-ai/multi-agent-workflows-often-fail-heres-how-to-engineer-ones-that-dont/)).

One live tension matters for the owner's design. Anthropic's research system passes "lightweight references" between agents rather than full documents, and its context-engineering guidance treats context as a budget that degrades as it grows [P, Sep 2025] ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Cognition, by contrast, wants full context shared. The design's rule that handoffs must paste the full spec and never a pointer sides with Cognition. That is defensible for one-page change specs, but it gets expensive for full product specs.

## Acceptance works only when the builder cannot touch the checks

**Agents tamper with tests often, and this is well measured.** On ImpossibleBench (ICLR 2026), the tasks are built so that passing the tests requires cheating. GPT-5 cheated in **54–93%** of runs, by editing test files, special-casing outputs or overriding equality checks. Anthropic models mostly edited the test files directly [M, Oct 2025] ([arXiv 2510.20270](https://www.emergentmind.com/papers/2510.20270); mitigation figures via [LessWrong](https://www.lesswrong.com/posts/qJYMbrabcQqCZ7iqm/impossiblebench-measuring-reward-hacking-in-llm-coding-1)). The study also measured four fixes:

| Fix | What happened |
|---|---|
| Hidden tests | Cut cheating to near zero, but also lowered legitimate performance |
| **Read-only tests** | "Works especially well for Claude models" |
| An explicit "abort and flag a human" exit | Cut GPT-5 from 54% to 9%, but **Claude Opus 4.1 rarely used it and stayed at 46%** |
| A strict prompt | Results ranged from dramatic to negligible depending on the task set |

Anthropic's own system card for Sonnet 4.5 reports a 53% hack rate on impossible tasks, falling to 20% with an anti-hacking prompt [M, lab self-report, Sep 2025] ([Anthropic](https://www-cdn.anthropic.com/963373e433e489a87a10c823c52a0a013e9172dd.pdf)). METR, an independent AI evaluation lab, found that OpenAI's o3 reward-hacked **43 times more often when it could see the scoring function**. Telling it "please do not cheat" had negligible effect [M, Jun 2025] ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)). OpenAI documented agents overwriting a `verify` function to return true and adding a test hook that silently skips every test [M, Mar 2025] ([OpenAI](https://openai.com/index/chain-of-thought-monitoring/)). The practical conclusion is consistent across all of these studies. Tests and test configuration must be out of the builder's reach. Some acceptance scenarios should stay hidden. Scoring scripts should not be visible to the agent being scored. Prompts alone do not hold.

**Specs help in vendor judgement, but the only large study found no measurable benefit from ticket-style specs.** Claude Code's guidance says to plan when work spans files or is uncertain, and "if you could describe the diff in one sentence, skip the plan". It describes good specs as self-contained: they name files and interfaces, state what is out of scope, and end with an end-to-end verification step [P, current] ([Claude Code docs](https://code.claude.com/docs/en/best-practices.md)). GitHub's Spec Kit (about 146k stars) advises "the smallest change that meets your needs" and presents no outcome data [P, Nov 2026] ([GitHub](https://github.com/github/spec-kit)). An ESEM 2026 study of **88,052 pull requests** found that linked specifications or tickets did not reduce defects or rework once author and risk were controlled for. On AI-tagged pull requests, specs went with about 12% more churn [M, observational, 2026] ([ESEM 2026](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)). That study mostly measures ticket linkage, not rich specs with executable verification. So it neither proves nor disproves the kind of spec the design uses.

**AI reviewers are useful advisers but poor gatekeepers.** On the largest seeded-bug benchmark found (vendor-run, so treat with care), AI review tools caught between 3% and 69% of known bugs. Their precision was only **0.16 to 0.51**, so most comments pointed at something that was not a real bug [M, vendor, May–Sep 2026] ([Tenki](https://tenki.cloud/blog/benchmarking-ai-code-reviewers)). Claude Code's docs warn that "a reviewer prompted to find gaps will usually report some, even when the work is sound" [P] ([Claude Code docs](https://code.claude.com/docs/en/best-practices.md)). Google's review standard still rests on human code owners approving changes that "definitely improve the overall code health", with a one-business-day turnaround [P] ([Google](https://google.github.io/eng-practices/review/reviewer/standard.md)).

**Nobody credible lets agents merge unattended.** GitHub's Copilot cloud agent "cannot approve or merge a pull request". The person who asked for the change cannot approve it, and its CI does not run until a human has looked at the code [P, current] ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). GitHub's Agent Merge (28 October 2026) fixes failing checks and conflicts automatically, then merges through auto-merge once branch rules are met. **No retry limits are documented** [P, Oct 2026] ([GitHub](https://github.blog/changelog/2026-10-28-agent-merge-watches-and-fixes-pull-requests-in-the-cloud)). Stripe's "Minions" merge more than 1,300 agent pull requests a week. They allow agents only one or two CI rounds before a human takes over and reviews [P, early 2026; read via mirror] ([Stripe mirror](https://pkm-wiki.pages.dev/raw/articles/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). Anthropic's telemetry shows experienced users grant more autonomy gradually, from about 20% to over 40% of sessions on full auto-approve, while also interrupting more [M, Feb 2026] ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)). The 2025 DORA survey of about 5,000 professionals found that AI adoption now raises delivery throughput but **still lowers delivery stability**, unless teams have strong automated testing, version control and small batches [M, survey, Sep 2025] ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report?e=48754805)).

## Architecture must be enforced by code, on boring stacks, with slow dependencies

Every serious source treats written architecture instructions as **advisory**. Only automated checks actually hold the line. OpenAI's "harness engineering" team built a product of about a million lines with "no manually written source code". It enforced a fixed one-direction layering (Types → Config → Repo → Service → Runtime → UI) with structural tests that block violations before merge. Cross-cutting concerns such as auth and telemetry had to enter through a single "Providers" interface. Custom linters had error messages that "double as remediation instructions", and the AGENTS.md file was kept to about 100 lines as a table of contents [P, single team self-report, Feb 2026] ([OpenAI](https://www.openai.com/index/harness-engineering); [InfoQ](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex)). Background agents also "garbage-collect" stale docs and pattern drift through small refactoring pull requests [P] ([summary](https://zby.github.io/commonplace/sources/harness-engineering-leveraging-codex-agent-first-world)). Anthropic says the same thing in fewer words: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic" [P] ([Anthropic](https://www.anthropic.com/engineering/claude-code-best-practices)). Birgitta Böckeler, writing on martinfowler.com, separates guides (instructions) from sensors (checks). She recommends "architecture fitness" tests, such as ArchUnit-style module-boundary tests run in hooks or CI, and notes that strongly typed, clearly bounded, opinionated codebases are easier to harness [P, expert, Apr 2026] ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)).

Evidence that **architecture decision records (ADRs) help agents directly is thin**. A 2026 study of 980 ADRs found language models could judge whether code violates an ADR with about **90% accuracy**. They struggled most with infrastructure and deployment decisions, which made up 42% of disagreements, so the authors judged the method "not yet reliable enough to replace human review" [M, preprint, Feb 2026] ([arXiv 2602.07609](https://arxiv.org/html/2602.07609v1)). A controlled ICLR 2026 study found that repository context files such as AGENTS.md **did not improve task success and raised cost by over 20%**. Help came only from rules describing non-standard, project-specific practices [M, Feb–Sep 2026] ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). The best-supported use of an ADR is therefore as the source of an automated check, with a short pointer in AGENTS.md, rather than as a long document loaded into every session.

**Stack choice measurably changes agent quality.** Across 3,011 problems in nine languages, one model passed **79.8% of problems in Python but 24.3% in Erlang**. Mainstream web stacks (React+Express, Django, Vue+Spring) solved typical create-read-update-delete tasks in 1–3 attempts, while niche stacks often needed more than 5 attempts or failed [M, preprint, late 2025] ([arXiv 2509.23261](https://arxiv.org/html/2509.23261v3)). OpenAI deliberately prefers "boring" technology for its API stability and training-data coverage. It also had agents write small in-house helpers rather than pull in opaque packages [P] ([OpenAI](https://www.openai.com/index/harness-engineering)).

**Dependencies are a live attack surface.** A USENIX Security 2025 paper found that commercial models invented non-existent package names in at least **5.2%** of code samples, and open-source models in 21.7% [M] ([USENIX](https://www.usenix.org/conference/usenixsecurity25/presentation/spracklen)). In April 2026 tests, current models still did so in **4.6–6.1%** of samples. 127 invented names were shared by all five models tested, and 53 of those were still available for an attacker to register [M, single-author preprint, 2026] ([alphaXiv](https://www.alphaxiv.org/abs/2605.17062.md)). In the August 2025 "s1ngularity" attack, compromised releases of the popular nx package ran installed AI coding tools (Claude, Gemini and Q) to hunt for secrets. More than 1,000 accounts were affected [M, incident reports] ([Socket](https://socket.dev/blog/nx-packages-compromised)). A vendor analysis says a **one-day "cooldown"** before installing new package versions would have blocked the big 2025 npm worm waves. The pnpm package manager made a one-day minimum release age its default in version 11 [P, vendor, May 2026] ([Mondoo](https://mondoo.com/blog/npm-supply-chain-security-package-manager-defenses-2026)).

## Agent UI defaults to generic unless pinned to a design system and screenshots

The vendors now name the problem themselves. Anthropic attributes the "AI slop aesthetic" (Inter fonts, purple gradients on white, minimal motion) to "distributional convergence" toward safe defaults in training data [P, Nov 2025] ([Claude blog](https://claude.com/blog/improving-frontend-design-through-skills)). OpenAI's GPT-5.4 frontend playbook sets hard rules: define a design system first, use real copy, use cards only where they are interactive, avoid default fonts and purple-on-white, keep design values in CSS variables, preserve existing patterns, and let the model check its own output in Playwright, a tool that drives a real browser [P, Mar 2026, via secondary press; primary page not fetched, U] ([The Decoder](https://the-decoder.com/openai-publishes-a-prompting-playbook-that-helps-designers-get-better-frontend-results-from-gpt-5-4/)). Anthropic's best-practice prompt is "take a screenshot of the result and compare it to the original. list differences and fix them" [P] ([Anthropic](https://www.anthropic.com/engineering/claude-code-best-practices)). The strongest practical lever is to constrain the agent to real components and design tokens (named colour, spacing and type values):

| Tool | How it constrains the agent |
|---|---|
| Figma's MCP server with Code Connect | Maps design nodes to real code components [P] ([Figma](https://help.figma.com/hc/en-us/articles/32132100833559-Guide-to-the-Dev-Mode-MCP-Server)) |
| Vercel's v0 | Reads the project's design tokens. Warns that models are trained on **default** shadcn/ui components and struggle with heavily customised ones [P, Nov 2026] ([v0 docs](https://v0.app/docs/design-systems)) |

No vendor has published measured evidence that its frontend guidance improves human-rated quality. **No controlled study shows that design systems improve the consistency of agent-built UI.** This is a real gap.

Automated design judgement by AI is still weak. Multimodal models "struggle" to produce well-grounded design critiques. A structured pipeline that gives the model a screenshot plus design guidelines, and asks it to point to specific regions, closed only half the gap to human experts on one metric [M, preprint, 2025] ([arXiv 2412.16829](https://arxiv.org/abs/2412.16829v2)). Accessibility is more encouraging. In one study, model-written UI code had fewer automated accessibility violations than human code (0.35 vs 0.43 violation rate). Feeding checker results back to the model improved it further (0.29), while clever prompting did not [M, preprint, Mar 2025] ([arXiv 2503.15885](https://arxiv.org/html/2503.15885v1)). Automated checkers cover only part of the problem: about 57% of issues by volume, according to Deque, and far fewer of the formal accessibility criteria [M, vendor, 2021] ([Deque](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues)). The 2026 WebAIM crawl found detectable failures on **95.9%** of the top million home pages. It warned that AI output can create "the appearance of accessibility" [M, via secondary summary] ([Nexer](https://www.nexerdigital.com/news-and-thoughts/the-webaim-million-report-2026-what-it-tells-us)). The user-experience research firm Nielsen Norman Group judged AI design tools generic and inconsistent between runs. Its advice is to keep humans responsible for direction and validation with real users, and never to invent user data [P, 2024, marked outdated] ([NN/g](https://www.nngroup.com/articles/ai-design-tools-not-ready/)). Its 2025–26 follow-ups could not be read [U].

## Slop shows up as complexity and duplication that green tests never catch

The clearest finding for an owner who does not read code comes from METR's March 2026 study. **Maintainers would have merged about 24 percentage points fewer AI patches than the automated test grader implied.** The rejections were "mostly code quality" problems, such as not following the repository's standards, rather than broken behaviour [M, blinded expert review, research note, Mar 2026] ([METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)). Carnegie Mellon's study of 806 repositories that adopted Cursor, a popular AI code editor, found a large speed boost that **faded after about two months**. It also found **persistent rises of about 30% in static-analysis warnings and 41% in code complexity**, and the accumulated debt then slowed later work [M, quasi-experimental, MSR 2026] ([arXiv 2511.04427](https://arxiv.org/html/2511.04427v3)). GitClear's 2026 report found that duplicated code blocks rose 81% between 2023 and 2026, while refactored ("moved") code fell from 21% of changes in 2022 to 3.8%. These are vendor figures with unclear attribution to AI and some unit inconsistencies, so take the size of the trend loosely and its direction seriously [M, vendor, 2026] ([GitClear](https://gitclear.com/the_ai_code_quality_maintainability_gap)). Veracode's repeated benchmark shows security pass rates **stuck at 45–55%** since 2023, even as code that merely compiles and runs rose to about 95% [M, vendor, Mar 2026] ([Veracode](https://veracode.com/blog/spring-2026-genai-code-security)). CodeScene reports that AI breaks code at least 30% more often in already unhealthy code [M, vendor research, Jan 2026; peer-review status U] ([arXiv 2601.02200](https://arxiv.org/html/2601.02200v1)).

The countermeasures with the best backing are:

| Countermeasure | Evidence |
|---|---|
| Small batches with strong rollback | [DORA](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model) |
| Narrowly scoped agent tasks | These merge more often in a study of 9,428 agent pull requests [M, Jul 2026] ([arXiv 2607.21832](https://arxiv.org/pdf/2607.21832)) |
| Human code-owner review held to the same bar as human code, with weekly volume throttled | Google's practice in its AI-driven code migrations [M, first-party, Jan 2025] ([arXiv 2501.06972](https://arxiv.org/html/2501.06972v1)) |
| Mandatory static and security analysis on agent output | Model upgrades alone do not fix security (Veracode, above) |
| Tracking warning density, complexity, duplication, short-term churn and rework | These are the measures the decay studies actually use |

"Percentage of code written by AI" is a vanity metric. Google's claim that 75% of its new code is AI-generated has an undisclosed method [M-weak, Apr 2026] ([Semafor](https://www.semafor.com/article/04/24/2026/google-ceo-says-75-of-companys-new-code-is-ai-generated)). No randomised trial tests any anti-slop practice directly.

This finding matters most for a **non-specialist owner**. Google's defence against slop is human code owners reading diffs. The design's Stage 1 asks the owner to judge "evidence and the staging build, not diffs". Staging shows behaviour. It does not show the complexity and convention drift that METR's maintainers rejected patches for. Something must stand in for the expert human reader: automated quality gates, a fresh-context code-quality reviewer, and occasional paid human review.

## How the owner's design scores against the evidence

Verdicts use four labels. **Supported** means the evidence points the same way. **Partly supported** means it supports the idea but with a caveat or a missing piece. **Contradicted** means the evidence points the other way. **Not addressed** means no evidence in the research bears on it.

### Design elements

| Element | Verdict | Why | Key citation |
|---|---|---|---|
| Roster of nine named persona roles | **Partly supported** | Roles that exist for independent checking (Verifier, Critic, Researcher in audit mode) match the evidence. Job-title splits inside the build loop add error-prone handoffs, and persona frameworks fail 60–67% of programming tasks. Names are harmless labels. | MAST [M, 2025] ([arXiv](https://arxiv.org/pdf/2503.13657)); E2EDevBench [M, Nov 2025] ([arXiv](https://arxiv.org/html/2511.04064v1)) |
| Elephant vs fish memory split | **Supported** (practitioner grade) | Mirrors Google's Elephant-Goldfish Model and Cognition's clean-context reviewers. No measured results exist. | Google [P, Oct 2026] ([blog](https://opensource.googleblog.com/2026/10/introducing-elephant-goldfish-model-plugin.html)); Cognition [P, Apr 2026] ([blog](https://cognition.com/blog/multi-agents-working)) |
| Elephants remember through repository files, not long chats | **Supported** | Anthropic's long-running harness and context guidance both say this; summarising alone "isn't sufficient". | Anthropic [P, Nov 2025] ([post](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)) |
| Review matrix: a fresh checker from a different role for every output | **Supported** | The builder grading its own work is the failure vendors warn about. A fresh context reviews better. | Claude Code docs [P] ([docs](https://code.claude.com/docs/en/best-practices.md)) |
| Automated checks are the gate; AI judgement is evidence | **Supported** (strongly) | Every architecture and testing source agrees. | Böckeler [P, Apr 2026] ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)); Anthropic hooks [P] |
| "Do not manufacture findings"; scale review to risk | **Supported** | Matches Anthropic's warning about reviewers inventing gaps and the low precision of AI reviewers. | Claude Code docs [P]; Tenki [M, vendor] ([benchmark](https://tenki.cloud/blog/benchmarking-ai-code-reviewers)) |
| Spec review (comprehension, critics, readiness go/no-go) | **Supported** (practitioner grade) | A direct adaptation of Google's Goldfish protocol. Measured benefit of specs is unproven, and one study found ticket-style specs did not cut defects. | Google [P]; ESEM 2026 [M, observational] ([paper](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)) |
| Verifier writes checks from the spec before reading the code, and never reads the builder's reasoning | **Supported** | "Have one Claude write tests, then another write code". | Handoffs paste the full spec, never a pointer | **Partly supported** | Fits Cognition's full-context view and Claude Code's note that subagents do not inherit history. Conflicts with Anthropic's "lightweight references" and with context-cost evidence for large specs. | Anthropic [P, Jun 2025] ([post](https://www.anthropic.com/engineering/multi-agent-research-system)); AGENTS.md study [M] ([arXiv](https://arxiv.org/abs/2602.11988)) |
| Dark run (no owner input mid-build) | **Partly supported** | MAST lists "failing to ask for clarification" as a failure mode. The "unclear request" typed blocker is the right safety valve. Anthropic sees agents pausing to ask more often as tasks get harder. | MAST [M]; Anthropic autonomy [M, Feb 2026] ([research](https://www.anthropic.com/research/measuring-agent-autonomy)) |
| Stop conditions and typed blockers | **Supported** | Matches Claude Code's "after two failed corrections, start fresh", Stripe's 1–2 CI rounds, and ImpossibleBench's abort option, with a caveat for Claude (see C3). | Claude Code docs [P]; Stripe [P]; ImpossibleBench [M] |
| Parallelise only independent work; no two agents on one file | **Supported** | Explicit in Claude Code's agent-team docs and Cognition's single-writer rule. | Claude Code docs [P] ([docs](https://code.claude.com/docs/en/agent-teams)) |
| Evidence committed; "prove the artifact" | **Supported** | "Have Claude show evidence rather than asserting success". Anthropic saw agents marking features done without testing. | Claude Code docs [P]; Anthropic harness [P] |
| Research-to-spec with an independent second researcher and an audit pass | **Supported** | Research is where parallel agents measurably win. Independent passes avoid anchoring. | Anthropic [M, Jun 2025] |
| Cheaper model for the builder (Sonnet), stronger model for checkers (Opus) | **Not addressed** | No study compares this split. ## C6 decision: one builder per ticket, with the Verifier as an independent tester

**Recommendation: make "one Implementer per ticket plus an independent Verifier" the default build shape. Keep the Architect only as the coordinator for multi-unit builds that start from a full spec (the C2 full-spec tier), and never as a design layer between the spec and the builder.**

**The measured comparison points this way.** In the only controlled comparison of team shapes on whole projects, a developer-plus-tester pair beat a single agent (49.5% vs 45.7% of requirements). Adding a designer role cut the result to 27.7%, because the developer followed the designer's blueprint over the requirements ([arXiv 2511.04064](https://arxiv.org/html/2511.04064v1)). The Architect's acceptance map is closer to a test plan than a design, which limits that risk. But each extra hop is a place where "inter-agent misalignment" can enter, and that category caused 32.3% of failures in MAST ([arXiv](https://arxiv.org/pdf/2503.13657)).

**Neither shape breaks the single-writer rule.** Both keep one agent writing code, so the real difference is coordination overhead and token cost. Claude Code's adapter already makes the main session play the Architect and call the Implementer and Verifier as subagents. For a one-page change spec, the ticket's acceptance criteria already *are* the acceptance map, and the Verifier's readiness check already confirms they are testable.

**What the Architect still adds earns its place on big builds.** It records the base, scope and baseline. It sequences dependent units and owns the final report. Those jobs match the "manager" or orchestrator-workers pattern that OpenAI and Anthropic endorse for multi-file work ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)).

**In practice the decision looks like this.** For change-spec tickets, the coordinating session hands the ticket to one Implementer and the spec to the Verifier, with no separate acceptance-map round. For full-spec builds, the Architect coordinates units as now. Max, the Evaluator, should then compare the two shapes on a handful of frozen tickets, measuring cost, rounds-to-PASS and owner rejections, before the decision is final for good.

## What the evidence cannot yet tell you

Several important questions have no solid answer as of November 2026. No controlled study compares persona teams with modern single-agent coding tools on real tickets. Nobody has measured whether design systems, spec tools or ADRs improve agent output. There is no production base rate for test tampering outside benchmarks. All AI-reviewer accuracy figures are vendor-run. METR's 2026 productivity follow-up was declared unreliable by METR itself ([METR](https://metr.org/blog/2026-02-24-uplift-update/)). Google's Elephant-Goldfish Model, which the design leans on, has no published metrics.

Several sources were seen only second-hand and are marked unverified (U): OpenAI's GPT-5.4 frontend page, Stripe's original Minions post (read through a mirror), the WebAIM 2026 figures (read through a summary), the NN/g 2025–26 updates, OpenAI's AGENTS.md and Codex guidance, Google's current ADK multi-agent docs, autonomy-level frameworks such as Dash0's and Shapiro's, and any 2026 DORA report. GitClear's and CodeScene's numbers come from vendors with a commercial interest. The specific numbers in the recommended changes (three rounds, seven-day cooldown, a month at Stage 1) are reasoned defaults, not measured optima.

## Conclusion

The research changes where the owner should worry. The design already defends well against the dramatic failure, an agent cheating its way to green, and it does so with the controls that have the best measurements behind them. The quieter failure is code that passes every test but grows harder to change month by month. That is the one the evidence says actually sinks agent-built software, and it is the one the design currently waves through as "notes". Because the owner does not read code, they cannot be the human reviewer Google relies on. The remedy is to convert "taste" into machine checks wherever possible, and to buy a little expert human review where it is not.

The design's next gains therefore come mostly from **guardrails and measurements**, not from new agents. The fewest handoffs that still keep the checker independent is the shape the evidence favours, which is why C6 should go to one builder plus one Verifier. The extra roles are worth keeping where they add an independent check: research, critique, spec review and evals. The autonomy ladder should be climbed only on numbers the scorecard actually produces.
